# 长程任务规范

长程任务的问题通常不是“Agent 不会做”，而是做着做着把中间研究当成成果、在 Phase 边界停住，或者下一轮继承了上一轮错误方向。

## 1. 从最终成果反推

任务开始先定义：

- 最终是谁使用
- 最终能看到/操作什么
- 哪些结果代表真正完成
- verifier 如何客观检查

再反推研究、数据、工具、接口和 UI。

如果最终目标是人用的工作台，研究脚本、数据探针、逆向工具、报告页面都不能替代工作台本身。

## 2. 研究与产品分离

需要未知数据/协议/第三方产品知识时，可以建设分析工具，但应保持：

```text
raw/source → analysis/research → ordinary artifacts/data → product/UI
```

最终产品不要直接依赖研究环境中的临时对象、不可移植序列化格式或人工步骤。

## 3. 阶段的意义

阶段用于降低风险和便于复核，不是停止条件。

一个好阶段应留下至少一种可验证增量：

- 可运行能力
- 可看的 UI/结果
- 可复用数据集/结构化产物
- 明确验证结论与证据
- 可重建的中间输出

阶段之间不要依赖“只有上一轮 Agent 脑中知道”的隐式状态。复用项目已有产物与版本机制，使输入/输出关系可以复核，保护不可重建输入；不要求按阶段新建目录树，也不要求永久保存每阶段输出。任务进度使用当前对话或已有任务载体，不能因此放宽 docs 准入。

## 4. 定期重构与产物规模

每个可验证阶段结束前，必须检查并重构本任务累积的代码；阶段内发现职责混杂、重复逻辑或文件持续膨胀时立即处理，不留到最终交付。

- 按职责拆分超长函数和超大源文件，合并重复实现，清理不再使用的实验分支、临时适配和废弃代码；不能靠增加抽象层或机械拆文件掩盖复杂度。
- 整理限于本任务涉及的实现，保护用户已有改动；通过相关测试/检查确认行为不变。涉及架构、核心模型或技术栈变化时，仍需先说明问题、现有能力缺口、最简方案、影响和验收。
- 禁止把持续增长的数据、日志、二进制或多阶段结果塞进一个超大 JSON、源文件、报告或序列化对象。优先采用项目已有分块、流式处理或存储能力，使部分读取、验证、重试和重建无需整量载入或重写。
- 以实际数据规模、内存占用、读写和重建成本检查产物设计；小型有界产物可以保持单文件。外部格式要求的单体输入/交付文件保留原格式，处理过程使用有界资源，不为拆分破坏兼容性。
- 及时清理可重建且不再使用的临时产物，保留必要来源与生成方式；不误删不可重建输入或用户产物。

复用已有测试、日志和规模限制，不另建“重构 workflow”、固定全仓行数配额或重型存储系统。

## 5. 可重建

对成本高或不可轻易重复的处理，保存足以重建的最小证据：

- 输入来源/版本
- manifest 或对象清单
- 转换/生成命令
- 关键参数
- 必要校验和/数量
- verifier 结果

不要求永久保存所有临时产物；能可靠重建的中间垃圾可以删除。

## 6. 自纠偏

每一轮都以当前工作树、真实数据、实际 UI/产物为准重新判断。

- plan/TODO/旧报告不是权威
- 前一轮 Agent 说“下一步做 X”不构成必须做 X 的理由
- 如果新证据证明路线错误，允许删除实验代码、回退、换方法
- 重复投递同一最终目标，本应形成纠偏环，而不是机械执行旧计划

## 7. 自主继续

没有以下阻塞时，完成一个阶段后应继续推进最有价值的下一步：

- 必须由人提供的账号、凭证、私有资料
- 付费或不可逆外部操作
- 破坏性数据变更
- 多个方向会造成重大产品/架构分叉，且现有目标不足以判断

普通可逆工程选择不需要让人反复选 A/B/C。

## 8. 最终验收

收尾时回到开头的 verifier，逐项给 evidence。

Evidence 可以是：

- 测试/命令输出
- 真实数据统计
- UI 可见结果
- 生成物路径/manifest
- 对照第三方事实的验证

“实现已提交”“Phase N 完成”“测试通过”只有在它们直接对应最终目标时才算完成证据。
