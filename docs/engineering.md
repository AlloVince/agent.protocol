# 工程行为规范

本文件解释模板中几条必须长期保留的工程规则。

## 1. Reuse-first

Agent 很容易在“只看当前目录”的情况下重造已有能力。协议要求在新建基础能力前扩大一次搜索范围：

1. 当前模块已有 helper/service
2. 当前仓其它模块
3. workspace / monorepo 内部 package
4. 正式 CLI / package scripts
5. 已声明的内部库、SDK、服务
6. 属于 `.super` 时检查其它子仓的共享能力

只有确认现有能力不适用，才新建。

这条规则针对的是“基础能力重复建设”，不是要求为了复用而制造远距离耦合。复用会明显损害边界时，应说明为什么不复用。

## 2. 人类可读代码

“能编译、测试绿”不是 Agent 代码的全部验收。

代码还必须让后来者快速看懂：

- 主流程在哪里
- 数据如何变化
- 哪些地方有副作用
- 失败如何传播
- 为什么存在特殊分支

优先显式、直接、局部可推理的实现。不要因为模型能生成复杂抽象，就把理解成本转嫁给人类。

## 3. 同一正式 CLI

如果某能力会被第二次使用，尤其是数据/运维能力，就应该进入项目正式操作面。

典型范围：

- import/export
- convert/normalize
- migrate/backfill
- index/reindex
- batch/repair
- inspect/verify
- deploy/ops

Agent 与人类应调用同一命令，避免出现“代码里有一个人类流程，Agent 又藏了一套脚本”。

一次性研究脚本可以存在于临时环境；当它开始承担正式流程，就必须收敛到共享库 + 正式 CLI。

## 4. CLI/长任务日志

对分钟级、批量级或可能失败后需要恢复的任务，日志至少要使人能判断：

- 正在做哪一阶段
- 大概推进到哪里
- 是否持续有进展
- 哪些对象失败/跳过
- 最终处理了多少、失败多少

不要让唯一反馈是“命令仍在跑”。

## 5. 低成本生产默认线

Agent 经常只做到“能跑”，漏掉几乎免费的生产常识。交付部署/服务配置前，要对照所用框架、反代、CDN 或平台的生产默认检查一次。

其中 HTTP 静态/文本压缩是明确基线：

- 如果 CDN/反代已经压缩，应用不重复做
- 如果没有上游承担，应用/服务器应为适合的文本类型启用 gzip/brotli 等压缩
- 已压缩媒体不强求二次压缩

同类检查还包括安全的静态缓存、合理超时、密钥来源、失败日志等。是否需要取决于当前系统；关键是不能因为 Agent 忘记而缺失。
