# 多仓 `.super` 规范

`.super` 用于一个产品/系统由多个独立仓组成时的全局上下文与调度。它不是要求所有项目采用的目录，也不是新的 Agent 私有配置格式。

## 1. 基本模型

例如：

```text
repo.super     # 系统级上下文
├─ repo.api     # 独立仓
├─ repo.web     # 独立仓
└─ repo.ops         # 独立仓
```

实际磁盘可为 sibling checkout、workspace 或远程仓；协议不规定布局。

`.super` 自己仍只使用普通社区文件：

```text
AGENTS.md
README.md
owner/
docs/
```

## 2. super 的职责

- 说明每个仓负责什么、不负责什么
- 保存跨仓主链路与关键契约
- 指出共享基础设施在哪里，防止重复建设
- 保存真正跨仓的 Agent 规则
- 组织跨仓任务的输入/输出/verifier
- 做最终集成验收

它不复制子仓内部实现文档。

## 3. Leadership

Leadership Agent 站在 super 层，从最终目标拆任务并调度子 Agent。

必须保证：

- 子任务边界尽量与仓职责一致
- 子任务有清楚的可验证交付物
- 子 Agent 进入仓后遵守该仓 `AGENTS.md`
- 跨仓接口变更由总 Agent 统一检查
- 最后验证的是系统结果，而不是“子任务状态全部 done”

## 4. Copilot

Copilot Agent 先读 super 获取系统地图，再进入具体仓工作。

super 帮它回答：

- 这个需求应该在哪个仓改？
- 有没有别的仓已经有同类基础能力？
- 改动会影响哪些契约/部署？
- 哪些规则是系统级的？

进入子仓后，局部代码风格、命令、测试和实现边界以子仓 `AGENTS.md` 为准。

## 5. 共享规则

把局部经验升级为共享规则需要门槛：反复跨仓发生、或本质属于系统边界、或能显著提高多个仓 Agent 的表现。

推荐在 super 的普通 docs 中维护一份最小共享规则/能力地图；文件名由项目自己决定，不是协议强制名。

当规则变化时：

- 语义比较各子仓现状
- 把独立进入子仓时必须知道的规则同步进子仓 `AGENTS.md`
- 只在必要时更新子仓 docs
- 不覆盖更具体的本地约束
- 不重复已经由代码/配置强制的事实

这样既保证子仓可独立工作，又不需要 `.ai/shared` 之类私有机制。

## 6. Protocol 升级顺序

对于多仓系统：

1. 查看 agent.protocol 新版本的通用行为变化
2. 判断哪些变化适用于该系统
3. 更新 super 的系统级约束
4. 再逐仓同步真正需要独立存在的条款
5. 做冲突检查，不整文件覆盖
6. 报告未同步项及原因

`owner/` 永远不作为自动升级目标。
