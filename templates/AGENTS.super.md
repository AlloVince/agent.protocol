# AGENTS.md — {{SYSTEM_NAME}}.super

## 定位

这是多仓系统的总上下文仓。它维护系统级事实、仓库职责、跨仓边界、共享能力与跨仓规则；不取代任何子仓自己的 `AGENTS.md`。

## 权威

1. 当前人类指令
2. 本仓 `owner/` 的系统级人类意图（若存在，默认只读）
3. 本文件
4. 子仓工作时：子仓中适用的 `AGENTS.md`（对其代码的局部规则更具体）
5. 代码、测试、schema、配置与真实运行结果
6. `docs/` 中仍有效的系统级 Agent 知识
7. 历史计划/报告

系统级目标与子仓局部规则冲突时，不要擅自覆盖；明确冲突并按当前人类目标解决。

## `.super` 应保存什么

只保存跨仓才有意义、且能帮助未来 Agent 的内容，例如：

- 子仓清单、职责、所有权与依赖方向
- 系统级主数据流、协议、部署关系
- 可复用的内部库、服务、CLI、数据能力与它们在哪个仓
- 多仓公共约束与反复出现的工程问题
- 跨仓任务的最终验收方式和必要证据

不要把每个子仓的内部说明复制一份到这里。

## Leadership 模式

适用于一个高层 Agent 统筹多个子仓/子 Agent。

- 从最终系统成果拆出可独立验证的子仓任务
- 为每个子任务写清输入、输出、边界、依赖与 verifier
- 子 Agent 进入子仓后必须遵守该仓 `AGENTS.md`
- 总 Agent 负责跨仓接口、一致性、集成与最终用户成果
- 不把“所有子 Agent 都完成”直接等同于系统完成；必须做整体验收

## Copilot 模式

适用于人/Agent 先从 `.super` 建立全局认知，再进入具体子仓工作。

- 先确认当前问题属于哪个仓、是否涉及共享能力或跨仓契约
- 进入子仓后，以子仓 `AGENTS.md` 为局部执行入口
- 仍需遵守 `.super` 中适用的系统级目标、依赖边界与共享规则
- 返回 `.super` 时更新真正有未来价值的系统事实；不要记流水账

## 跨仓复用

新增基础能力前必须先查系统已有能力。尤其检查：

- 其他子仓已存在的内部库/SDK
- 已有统一 CLI 或转换/迁移/索引工具
- 已有认证、存储、通知、抓取、导入等基础设施
- 已有跨仓协议与数据模型

默认优先复用/扩展已有能力，而不是在每个仓重新造一份。

## 共享规则的形成与同步

共享规则不是把所有局部经验上收。

只有当一个问题：

- 在多个仓反复出现，或
- 明显属于系统级边界，或
- 能稳定减少多个子仓 Agent 的误判/返工

才进入 `.super` 的共享规则。

同步时：

1. 先在 `.super` 中形成最小、技术无关的规则
2. 逐仓语义比较当前 `AGENTS.md`，只加入适用部分
3. 保留子仓本地更具体的规则，不整文件覆盖
4. 发现冲突时报告原因，不静默选边
5. 子仓如果已经通过代码/原生配置解决，不再复制多余文字

共享规则的目的，是让独立进入任一子仓的 Agent 也能得到必要约束，而不是建立新的私有配置系统。

## Protocol 升级

升级 agent.protocol 时：

- 先比较新旧通用规则，不机械复制模板
- 先更新 `.super` 中真正适用的系统级规则
- 再检查哪些通用规则需要传播到子仓
- 不覆盖子仓业务约束，不修改 `owner/`
- 一次升级应能解释：新增了什么行为约束、哪些仓受影响、哪些没有同步以及原因
