## 权威与事实

1. 当前人类指令
2. `owner/` 中与任务相关的人类长期意图（若存在）
3. 本文件与更近目录的 `AGENTS.md`
4. 可执行事实：代码、测试、schema、配置、lockfile、CI/部署配置
5. `docs/` 中仍被验证有效的 Agent 文档
6. 历史 plan、TODO、旧报告

`owner/` 默认只读。除非当前人类明确要求修改具体 owner 文件，否则不得创建、整理、重写或删除其中内容。

历史计划不是事实。冲突时重新验证当前实现与真实产物，不为保住旧结论而扭曲代码。

## 开始工作

- 先明确用户真正要得到的结果、范围与可观察完成条件
- 阅读与任务直接相关的 `owner/`、`docs/`、代码、测试和原生配置；不要无目的整仓扫描
- 新建能力前，先搜索当前仓、workspace、内部包、已有 CLI、已有服务和已声明的共享基础设施
- 若项目属于 `.super` 系统，新增基础能力前先检查 `.super` 的仓库职责与共享能力
- 可逆、低风险且下一步明确时直接推进；不要把普通工程选择反复抛回给人类

## 复用优先

已有基础设施优先于新造：

- 已有领域库 / SDK / workspace package
- 已有正式 CLI / package scripts
- 已有数据导入导出、转换、迁移、索引、批处理、修复工具
- 已有基础服务、适配器、配置与部署模式
- `.super` 中声明的跨仓共享能力

只有在现有能力确实不能满足需求时才新增。新增前说明现有能力缺口；优先扩展正确的已有层，而不是在业务代码旁边复制一套近似实现。

不得为了“更快”绕开项目已有抽象，留下第二条永久路径。

## 代码给人读

Agent 生成的代码与人写代码执行同一质量标准。

- 首选清晰命名、直接控制流、显式数据变换与显式副作用
- 函数/模块职责应能快速看懂，避免把简单逻辑压成难读表达式
- 不用元编程、魔法封装、生成式样板或层层 helper 掩盖业务流程，除非现有代码本来如此且确有收益
- 注释解释“为什么”和非显然约束，不逐行翻译代码
- 不为追求少行数牺牲可调试性和可维护性
- 修改后问自己：一个不了解这次对话的人能否仅靠代码、测试和必要 docs 继续维护？

## 人类与 Agent 共用同一操作面

构建、测试、数据转换、导入导出、迁移、索引、批处理、修复、回填、部署和常规运维，必须优先通过项目正式 CLI / package scripts / 标准任务入口执行。

- Agent 使用的命令、参数语义和结果应与人类使用方式一致
- 常规能力缺失时，先补/扩展正式 CLI，再通过它完成任务
- 不得把临时脚本、一次性 REPL、私有路径变成唯一可用的生产/运维流程
- 允许为一次性调查写临时 scratch 代码，但不得把它提交为常规操作入口；结论若进入正式流程，应落回正式 CLI/库

## 可观察性

CLI、批处理和长任务不得长时间静默运行。适用时至少输出：

- 当前阶段
- 已处理数量 / 总量或可理解的进度
- 失败/跳过项及原因
- 关键耗时或吞吐（有诊断价值时）
- 最终成功/失败摘要与退出状态

日志是操作界面的一部分，不应只在进程结束时给一个模糊状态。

## 工程与生产默认线

不要漏掉成熟、低风险、几乎无业务代价的基础工程默认项。使用框架/平台推荐的生产配置，并检查与当前部署层是否重复承担。

典型例子：

- HTTP 静态/文本内容应启用合适的压缩；若 CDN/反代已统一处理，则不要重复压缩
- 可安全缓存的静态资源应使用合理缓存策略
- 长请求/外部调用要有合理超时与失败处理
- 密钥不进入仓库；环境差异通过正式配置表达
- 服务/批任务失败要留下可诊断信息

这不是要求机械堆配置；如果明确不采用一个常识性默认项，应有具体原因，而不是遗漏。

## 改动纪律

- 解决当前真实问题，不为假想未来提前拆服务、加层或引依赖
- 不混入无关重构、升级和格式化大改
- 不静默改变公共接口、数据语义或系统边界
- 高返工成本或存在多个真正可行架构方向时，先做设计判断；可逆的小选择直接做
- 架构改动先再次检查：现有能力能否扩展，而不是新增一套

## 文档

`README.md` 与 `owner/` 主要面向人类；`docs/` 只为未来 Agent 服务。

只有满足至少一项才写/保留 docs：

- 能显著减少未来 Agent 的误判或重复研究
- 能减少反复加载大量代码才能恢复的上下文/Token 成本
- 保存代码/测试难以表达的边界、外部事实或关键约束
- 保存高返工决策及其理由/弃选方案
- 支持跨 session 的长任务继续、复核或重建

不要记录：

- git 已经清楚表达的流水账
- 只对当前会话有意义的临时推理
- 可从代码/测试/配置一眼恢复的重复说明
- 为了“文档完整”而创建的空分类

过期 docs 比缺失 docs 更危险：发现失真就修正或删除。

### Design / ADR

不要求每个任务写 Design。

- 短期、可逆、实现后代码即可自解释的设计：留在当前任务，不落文档
- 会长期指导后续实现的结构/协议/数据流设计：写入普通 `docs/`，名称按项目习惯
- 高返工、跨模块、涉及明确取舍且未来 Agent 需要知道“为什么”的决定：写 ADR（若项目使用 ADR）
- 不重复保存实现已经完全说明的内容

## 长程任务

长任务围绕最终用户可见/可用成果推进，而不是围绕 Phase 数量推进。

1. 先定义最终成果与 verifier：完成时人能看到/使用什么，如何客观验证
2. 从最终界面/产物反推中间步骤；研究、逆向、实验工具只是手段
3. 对不熟悉的外部产品/设备/协议，先调查真实产品与公开资料，再决定模仿或实现方式
4. 分阶段时，每阶段都留下可复核、可继续、必要时可重建的成果；有文件/数据产物时使用独立目录或等价隔离方式，禁止阶段间相互覆盖；不要依赖未记录的隐式状态
5. 原始输入、manifest、转换规则、校验和、生成命令等，只在它们对重建/追责有价值时保留
6. 面向分析/逆向的工具与最终人类 UI/产品职责分离；前者不能冒充最终成果
7. 每轮重新检查当前代码、数据和实际产物；旧 plan/TODO/前一轮 Agent 结论只能作为线索
8. 发现方向错误可以回滚、删除实验代码或改路线，不为维持历史投入继续错下去
9. 没有账号/凭证/付费/破坏性操作/不可逆决定/重大产品或架构歧义时，下一步明确就继续推进，不因完成一个 Phase 自动停下
10. 结束时按最初 verifier 反向逐项验收，并给出真实 evidence；“代码写完了”不等于任务完成

## 测试与交付

- 运行与改动范围匹配的测试/检查；不要为了绿灯删除或弱化测试
- 对失败、未验证项和环境限制如实说明
- 交付摘要至少包含：完成了什么、如何验证、关键证据、剩余真实问题
- 除非人类明确要求，不自动 commit / push / release
